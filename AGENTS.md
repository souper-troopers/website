# Souper Troopers Website

## Stack (decided 2026-08-08 — do not change without asking the user first)
- **Framework:** Astro
- **Interactivity:** Svelte 5, using **runes** syntax (`$state`, `$derived`, etc.) — not Svelte 4 stores or `export let` reactive statements. If unsure which syntax an example uses, default to runes.
- **Content:** Sanity (headless CMS), project `wqa0no5g` / dataset `production`. Schema lives in `studio/schemaTypes/` in this repo; content lives in Sanity's hosted dataset, fetched at build time via `src/lib/sanity.ts`. Live since 2026-08-08 — six types (`successStory`, `teamMember`, `partner`, `product`, `impactStat`, `siteSettings`), all wired into the site's pages. Structural/rarely-changing copy (CAST steps, Humanity Hub services list, hero headline) intentionally stays hardcoded in `.astro` files, not in Sanity.
- **Hosting:** Vercel or Netlify (static/JAMstack deploy, auto HTTPS/CDN, no server to maintain).
- **Shop/checkout:** ~~Stripe Checkout or Snipcart~~ **corrected 2026-08-09**: Stripe doesn't support South African merchant accounts directly (routes through Paystack, its African arm), and Snipcart has no native Paystack support (would need a fully custom gateway integration, defeating the point of using Snipcart). If real checkout is built, it's **Paystack direct** — own cart, one small piece of backend automation to hand off to Paystack's hosted payment page. See `docs/shop-checkout-decision.md` — whether to build this at all yet (vs. staying with the current manual request-and-confirm flow) is still open, pending Kerry's read on actual order volume.
- **Donations:** link out to the org's existing/new donation platform rather than building custom payment infra.

## Working agreement
- The user must be consulted before any tech/stack choice or change — do not swap frameworks, CMS, or hosting providers unilaterally.
- **Content backups (built 2026-08-09)**: `.github/workflows/sanity-backup.yml` exports the production Sanity dataset weekly and pushes it to a separate **private** repo, `souper-troopers/website-backups` — kept out of this (public) repo since exports likely contain personal data (beneficiary names/stories, contact details, unpublished drafts). Both required secrets are set on `website`: `SANITY_API_TOKEN` (Viewer/read-only) and `BACKUP_REPO_TOKEN` (fine-grained PAT, write-scoped to `website-backups` only). **Gotcha (corrected 2026-08-09 — worse than first thought)**: GitHub requires a workflow file to exist on the **default branch** before it can be run *at all* via `workflow_dispatch` — not just for the `schedule` trigger. Confirmed by trying `gh workflow run` against `dev`: 404, "workflow not found on the default branch." So this can't even be test-run until merged to `main`, not just left to activate its cron later. This also doubles as the migration path if ever needed.
  - **Hardened 2026-08-11 — three additions, none of them yet run in CI.** The workflow now (a) verifies the export before trusting it, (b) applies a retention policy, and (c) emits a heartbeat to an external monitor. **The cron only ever reads `main`**, so none of this is live until `dev` is merged; every Sunday before that takes a backup with the old, unchecked workflow.
    - **Verification step** — rejects the export if the archive is missing/under 10KB, has no `data.ndjson`, contains fewer than 25 documents, or contains **zero assets**. Motivation: `sanity dataset export` can exit 0 having produced something useless (most plausibly a narrowed/partially-revoked API token returning a fraction of the documents), and without this that tarball gets committed *and* reported as a success — a green monitor guarding a worthless archive. Documents and assets are fetched in separate passes, hence the separate zero-asset check; a text-only backup would lose every image on restore. Tested against six synthetic tarballs, not in CI. **25 is a catastrophe floor, not a correctness check** — it catches 42→3, not 42→30. Catching that needs comparing against the previous backup, which means moving the repo clone ahead of the verify step; deliberately deferred as it means reordering an untestable workflow.
    - **Retention policy** — every weekly for 8 weeks, then first-of-month for a year, then first-of-year forever. Every snapshot is a *full* copy (documents + assets), not a diff, so without this the folder grows by a complete copy of the site's content every week. Simulated over 3 years: settles at ~22 files instead of 157. Has an abort guard — a policy that would delete today's backup or all backups is treated as a bug, not a valid outcome. **`git rm` does not shrink a git repo**: pruned blobs stay in history, so this caps what you *see*, not what GitHub *stores*. Irrelevant at current sizes (all product images are ≤600px); becomes real if the high-resolution originals we're asking Kerry for ever land, at which point GitHub Releases (which delete cleanly) is the migration.
    - **Dead-man's-switch, not failure alerting.** Every likely failure here is *silent*: a disabled schedule doesn't run, so it doesn't fail, so nothing notifies anyone. The workflow pings an external monitor (`HEALTHCHECK_URL` repo secret) on success and `/fail` on failure; the monitor alerts when a weekly ping *doesn't arrive*. The job can therefore only ever prevent an alert by succeeding — it can never make silence look like success. **Deliberately external to GitHub**: a monitor must not share fate with the thing it monitors, and two of the three failure modes below are GitHub itself stopping.
  - **The two things that will silently kill this** (both unresolved as of 2026-08-11):
    1. **`BACKUP_REPO_TOKEN` expires Tue 8 September 2026** (confirmed 2026-08-11). It's a fine-grained PAT and those carry a mandatory expiry. When it lapses the push step fails every week forever — with the heartbeat live this at least alerts, but it still needs a human to rotate it. Not reachable via API (`/orgs/{org}/personal-access-tokens` 404s unless the org enforces PAT-approval policies, and needs `admin:org`); read it manually from the creating account's Settings → Developer settings → Fine-grained tokens. **Note this falls *before* the 19 Oct checkpoint below, so it is the next thing due.** The permanent fix is a **deploy key** on `website-backups` instead of a PAT — deploy keys don't expire and are scoped to the single repo, which is both safer and less maintenance; it needs the clone/push switching from HTTPS to SSH.
    2. **GitHub disables scheduled workflows after 60 days of repo inactivity.** Invisible while the repo is busy; near-certain once the site launches and commits stop.
  - **Checkpoint — Mon 19 Oct 2026**: the first run that actually prunes anything is **Sunday 18 October 2026**, dropping `production-2026-08-16.tar.gz`. Open that run's "Apply retention policy" step and confirm the log reads `Retention: kept N, pruned 1: ...` rather than "nothing to prune". Note `production-2026-08-09.tar.gz` is the earliest backup, so it is both the first-of-month and first-of-year anchor and is **kept permanently** — don't read its survival as a bug.
- **Git workflow (added 2026-08-09, cost-driven):** do day-to-day commits on the `dev` branch, not `main`. Netlify auto-deploys `main` on every push (a production deploy, 15 Netlify credits each on the Free plan — 300/month total) and pushing every small commit straight to `main` burns through that fast. Push to `dev` freely (no production-deploy cost), then merge `dev` → `main` only when actually ready to ship a batch of changes to the live preview.
  - **The full credit picture (confirmed against Netlify's docs 2026-08-12, after the team hit its cap mid-cycle).** Metered: **production deploys 15 credits each**, web bandwidth **20 credits/GB**, web requests **2 credits/10,000**, functions compute **10 credits/GB-hour**. **Not metered at all: branch deploys, deploy previews, and failed deploys** — so the `dev` workflow above genuinely costs nothing, and Netlify Forms submissions are free too. At this site's traffic, bandwidth and requests are noise; **production deploys are effectively the entire bill**, which puts the Free plan at exactly **20 production deploys per month**. That's ample for the post-launch steady state (Kerry edits a batch in Sanity, then one manual redeploy) and tight during a build phase like 8–12 August, which is what exhausted it.
  - **Branch deploys are the free escape hatch when credits run out.** Production deploys pause; branch and preview deploys keep working. A branch deploy of `dev` gives a stable URL to show Kerry at zero cost — worth reaching for before paying to raise the ceiling.
  - **Plan-change timing is asymmetric.** Upgrades take effect *immediately*, reset the billing cycle, and are prorated; downgrades wait for a cycle boundary and are not prorated, and unused credits are wiped when they land. So a "just for this month" upgrade may bill for two. Personal is $9/mo for 1,000 credits (~66 production deploys). Neither Free nor Personal rolls credits over.
  - **Ruled out as a credit drain (checked 2026-08-12):** the Sanity → Netlify rebuild webhook. `sanity hooks logs "Netlify rebuild" --project-id wqa0no5g` shows exactly four fires, all on 2026-08-09 between 06:25 and 06:33 — the original verification run — and nothing since. It is still disabled as intended. Re-check this first if credits ever vanish unexplained, since a re-enabled hook spends 15 credits per Sanity save.

**Sanity gotcha — document IDs must not contain a dot (found 2026-08-10):** Sanity treats any document whose `_id` contains a `.` as a *private* document, readable only with an authenticated token. Creating docs with tidy namespaced ids like `bbbeeBenefit.esg` succeeds and they show up in the Studio and in token-authenticated queries, but the site's tokenless client (`src/lib/sanity.ts`) silently gets `[]` back — no error, just an empty section. Use hyphens (`bbbeeBenefit-esg`) or Sanity's generated random ids instead. Worth checking first if a Sanity-driven section ever renders empty despite the content existing.

## Publish → rebuild pipeline
This is a static site (`output: "static"`) — pages are pre-rendered once at build time, so a Sanity edit alone doesn't change the live site. A Sanity webhook ("Netlify rebuild", id `IQSKUBSymrG2dmll`) POSTs to a Netlify build hook whenever a document changes in `production`, which triggers a fresh `astro build` and redeploy. Verified working 2026-08-09.

**⚠️ Disabled (`isDisabledByUser: true`) since 2026-08-09 — and decided (2026-08-10) to stay off deliberately**, not just paused during Studio experimentation. Per-edit auto-rebuild costs a 15-credit Netlify production deploy on every single Sanity save; manual redeploy after a batch of edits is more cost-effective and is now the intended workflow going forward (including post-launch). The hook itself is being left configured (not deleted) in case auto-rebuild is ever wanted again — re-enable by PATCHing `{"isDisabledByUser": false}` to `https://api.sanity.io/v2025-08-04/hooks/projects/wqa0no5g/IQSKUBSymrG2dmll` if that changes. Until/unless re-enabled, content edits in Sanity will NOT show up on the live site without a manual deploy — via the Deploys page (https://app.netlify.com/projects/souper-troopers/deploys?filter=main → "Trigger deploy"), or hitting the build hook URL directly. This is Kerry/Shan's normal publish step now; see "Kerry & Shan need access to" below.

**Gotcha if this ever needs recreating:** Sanity's webhook API (`POST /v2025-08-04/hooks/projects/{projectId}`) accepts a hook with `rule: null` without complaint, but a null rule silently matches nothing — the hook exists and looks fine in `sanity hooks list`, but never fires, with zero entries in `sanity hooks logs`. It needs an explicit rule set via `PATCH`: `{"rule": {"on": ["create", "update", "delete"], "filter": "true"}}`. Confirmed via the webhook's `attempts` endpoint (`GET /v2025-08-04/hooks/projects/{projectId}/{hookId}/attempts`) — that's the reliable way to check whether a webhook has actually ever fired, rather than trusting that "exists" means "works."

## "Publish" button in the Studio (built 2026-08-12) — replaces giving Kerry & Shan Netlify logins
Since auto-rebuild is deliberately off (above), publishing is a manual step. The plan until now was to invite Kerry/Shan to the Netlify team and send them the Deploys page. **That plan doesn't work on the current plan tier**: Free and Personal are both "Audience: Individual", and **Pro ($20/mo) is the only Netlify plan with team members at all** (unlimited, no per-seat cost). So the documented approach silently required a $20/mo upgrade.

It isn't needed. **Build hooks require no authentication** — Netlify's own wording is that the URL "contains a unique, non-guessable path but no other form of authentication" — so anyone holding the URL can publish, with no Netlify account. The button lives where the editing already happens:

- **`studio/tools/PublishTool.tsx`**, registered via `tools: (prev) => [...prev, …]` in `sanity.config.ts` (**the function form, not an array** — an array replaces the plugins' own tools and would drop structure + vision).
- **`netlify/functions/trigger-deploy.mts`** does the actual POST. **The Studio never learns the hook URL**, which is the whole point: the hook URL is a bearer credential worth 15 credits per use out of a 20-deploy monthly allowance, and it is currently *genuinely* secret — it lives only in Sanity's webhook config and the Netlify dashboard, and has never been committed to this public repo (verified across full git history). Putting it in the Studio would publish it, since the Studio's JS bundle is served openly even though its content needs a login.
- **What the origin check does and doesn't do**: `Origin` is browser-set and unforgeable by another *webpage*, so it stops a malicious site triggering deploys through a visitor; it does nothing against curl. The cooldown is per-Lambda-instance, so it's a brake on double-clicks and retry loops, not a lock. **Real containment: the credential never leaves the server**, so abuse is stopped by deleting/renaming the function — no hook rotation, no Sanity reconfiguration. Next step if ever needed is a passphrase in the Studio's local storage, deliberately not built (one more thing for Kerry to lose, for little gain).
- **Two prerequisites before this works.** (1) `NETLIFY_BUILD_HOOK_URL` must be set in Netlify → Site configuration → Environment variables (and in `.env` for local `netlify dev`); the function fails loudly with a readable message until it is. (2) The function must actually be deployed — **don't `sanity deploy` the Studio before the function is live on `main`**, or Kerry gets a button that errors. `TRIGGER_URL` in `PublishTool.tsx` is the `netlify.app` preview host and needs updating at launch with the other domain items.
- **Gotcha — `@sanity/icons` v5 moved to per-icon subpaths**: `import {RocketIcon} from '@sanity/icons/Rocket'`, not from the package root. The root barrel is now a lazy registry that no longer re-exports the components, while its `.d.ts` still declares every name — so a root import **typechecks cleanly and then fails the build** with "Missing export". `@sanity/ui` and `@sanity/icons` are now explicit `studio/` dependencies rather than relying on hoisting, since CI runs `npm ci`.

## Shop discoverability (built 2026-08-11)
Context: Kerry bought a Shmiley domain hoping to make the products more findable by search engines and LLMs. **The second domain was the wrong lever** — indexability is a property of pages, not hostnames, and splitting the catalogue onto a brand-new domain would have meant duplicate content plus zero accumulated authority. What was actually missing was on this site, so it got built here:

- **Per-product pages** — `src/pages/shop/[category]/[item].astro` → `/shop/worry-dolls/african-worry-doll-madiba`. Before this, 11 items shared 3 category URLs, so no individual product could be ranked, linked or cited. Category pages (`[slug].astro`) are unchanged as the parent listing.
  - **Only `displayMode === "items"` categories get child pages.** An `attributes` category (currently just Coffee) is one product sold in variants, so its category page *is* its product page — it carries a `Product` with one `Offer` per `attributeVariant` instead. Don't "fix" the missing `/shop/coffee/<item>` routes; there are deliberately none.
- **`Product` + `Offer` + `BreadcrumbList` JSON-LD**, emitted via a new optional `jsonLd` prop on `Layout.astro` (an array of schema.org blocks, rendered as extra `<script type="application/ld+json">` tags alongside the site-wide `NGO` one). `Layout` also gained `ogType` and `ogImage` props so a shared product link previews the actual product photo.
  - **`brand` and `seller` are both "Shmiley"** (decided 2026-08-11). Shmiley (Pty) Ltd is factually the trading entity regardless of how Kerry answers the domain question, and naming it consistently starts building the Shmiley entity association now — which is exactly what carries over if a standalone storefront is ever built. Change in one place if that decision reverses.
  - **Trailing slashes in structured-data URLs must match Astro's canonical/sitemap URLs** (which have them). Structured data disagreeing with the `<link rel="canonical">` on the same page reads as two URLs for one product. Both product and category pages build these explicitly — don't drop the trailing slash.
- **`shopItem` schema gained `slug`, `details` and `soldOut`** (`studio/schemaTypes/shopItem.ts`).
  - **`slug` is deliberately NOT required**, and `src/lib/sanity.ts` falls back to a `slugify(name)` at build time. The 11 items migrated from WooCommerce predate the field, so without the fallback every one of them would have had no product page until someone hand-generated slugs in the Studio — this avoided needing any Sanity write/migration at all. Trade-off: renaming an unslugged item silently changes its URL. The schema field description nudges Kerry to set an explicit slug once a product is out in the world. **The generated slugs are long** (`gift-tag-india-harris-pack-of-5`) because they come from the full product names — fine, but worth tidying by hand in Sanity before launch.
  - `soldOut` is a manual toggle, not inventory tracking (still deliberately absent — see `docs/shop-checkout-decision.md`). It hides Add to cart and flips `availability` to `OutOfStock`.
- **Product photos — the two gift tags are fixed (2026-08-15), the rest are not.** `Gift Tag - India Harris (pack of 5)` and `Gift Tag - Hans Moolman (pack of 3)` now carry 1800×1800 crops of the real originals, replacing 600×203 and 600×166 scrapes that were being stretched to ~3× and ~2.5×. Three things deliberately left alone:
  - **The coffee.** `photo-output_0` is the *same shot* as the current 600×600 category image at 3840×3840 — but it carries a **Souper Troopers watermark** and a studio background, where the current one is a clean cutout on white. That's a trade, not an upgrade, so it's the client's call. Asked on the RFC page.
  - **The `gift-tags` category tile is still 600×166**, and the shop landing page asks for `width(500).height(375).fit("crop")` — so it is upscaled ~2.3× *and* centre-cropped to an arbitrary middle slice of what is actually a lay-flat of six tags. No single new photo reproduces that composition, so fixing it means either choosing one pack shot to stand for the category or rebuilding the lay-flat. Both are design decisions, not swaps.
  - **The `worry-dolls` category tile (600×364)**, for the same reason.
- **Still outstanding — real product descriptions, now 1 of 12 in.** Shan sent a full African Worry Dolls description on 2026-08-15; it's live on the `productCategory` for `worry-dolls` (three Portable Text paragraphs, near-verbatim — only the repeated `African Worry Dolls™` opener was dropped, since the page heading already says it, and with it the question of whether the site should assert a ™). **Left at category level, not copied onto the 9 dolls**: it describes the product line, and duplicating identical text across 9 pages is what search engines treat as thin content. Each doll still needs a line or two on what makes *that* one different, and the coffee and the two gift tags still have nothing at all. `details` remains empty on every item, so most `Product` blocks still ship without a `description`. Blocked on the client, not on code.

## Core-site discoverability (built 2026-08-12)
Prompted by the user searching "homeless charities cape town" and finding the *existing* site nowhere. The shop work above had covered products; the mission side had never been looked at. Audit found the site said "homeless"/"homelessness" **three times in total** — twice mid-paragraph in `about.astro`, once in product boilerplate — and in zero titles, descriptions or `<h1>`s. Every `title=` was the nav label ("Our Work", "Who We Are", "Get Involved"). Nobody searches those, so there was nothing for Google to match.

- **Titles/descriptions rewritten** on `index`, `about`, `our-work`, `get-involved`, `donate`, `contact`, `shop/index` from nav labels to descriptive, query-shaped ones. **`Layout.astro` appends `" - Souper Troopers"` (18 chars)** to every title, so the per-page part must stay ≈40 chars or the whole thing truncates in results — don't add the org name again in a page's own title. Two rules learned by getting them wrong (corrected 2026-08-12):
  - **Keep ` - ` out of a page's own title.** The suffix already supplies one separator, so a title carrying its own produced three flat segments — `Donate - support our work in Cape Town - Souper Troopers`. Commas are fine; a second dash is not.
  - **The homepage is brand-first and passes `rawTitle`**, which skips the suffix entirely. `Souper Troopers - homelessness charity in Cape Town`, not the reverse. A front door should be identified by its name before its category — the automatic suffix can only ever produce "descriptor - Brand", which reads like a directory entry, and for an organisation whose framing is "we are all human" it puts the label ahead of the identity. No real SEO cost: the whole title is read either way, and Google frequently rewrites homepage titles regardless. Every other page reads correctly with the brand last.
- **`NGO` JSON-LD gained `areaServed`, a structured `PostalAddress`, and `sameAs`** (the five footer social URLs, reusing the existing `socialLinks` array). Without these nothing told Google this is a *Cape Town* entity. `description` was the brand tagline ("We are all human…"), which never says what the org does or where — now a factual summary. **`addressLocality`/`addressRegion`/`addressCountry` are hardcoded constants**, since Sanity's `address` is one flat string; a trailing `, Cape Town` is regex-stripped off `streetAddress` so the city isn't stated twice. If the org ever moves city, those constants need changing alongside the Sanity value.
- **`<h1>`s deliberately left alone.** Titles and descriptions are invisible to visitors, so they're safe to change unilaterally; an `<h1>` is Kerry's visible copy and it matches the nav label, which is coherent UX. Changing those is a proposal, not a fix.
- **The "homeless" vs "people experiencing homelessness" tension is real and is Kerry's call.** The dignified phrasing is what the site uses and is almost certainly deliberate; it's also close to unsearched. Resolved *provisionally* as: her language in on-page copy, the plainer word in `<title>`/`<meta description>` only. Applied, and flagged on `request-for-comment` for her to veto — don't treat it as settled.
- **Not the website, and probably the bigger lever: Google Business Profile.** "homeless charities cape town" is a local-pack + listicle query; the map block comes from GBP, not from any site, so no amount of work in this repo can win it. **`docs/google-business-profile.md` holds the full prepared listing content** — exact NAP, categories, a 726-char description, hours, photo list. The **Kerry-facing version is a real page on the site**, `/google-listing` (`src/pages/google-listing.astro`), linked from the Google-listing question on `/request-for-comment` — chosen over a standalone artifact so the walkthrough is versioned with the project and needs no separate sharing step. Keep it in sync with the doc; opening hours are imported and the character count is measured at build time, but the address, categories and description text are duplicated across the two. Claiming/verifying it is not codeable (needs a Google login and postcard/phone/video verification) and must be done on an *organisation* Google account, not a volunteer's personal Gmail — same ownership reasoning as the account checklist. Existence/ownership unknown; asked on the RFC page.
- ~~**There is no phone number for Souper Troopers anywhere**~~ — **answered 2026-08-15 by Shan: there is no direct line, email only.** Offering "email-only is fine" as a valid answer rather than presuming an oversight is what got it answered in one line. The GBP phone field now reads "leave it blank" rather than sitting empty and unexplained, with a warning not to substitute a personal mobile — the obvious way someone fills that box under pressure, and whatever goes in it is public and permanent. Stop treating it as a gap.
- **Address constants now live in `src/lib/address.ts`, not inline in `Layout.astro`** (moved 2026-08-15, when Shan confirmed the postal code as **7925** for 66 Newmarket Street specifically, not just for Woodstock generally). Same rationale as `opening-hours.ts`: the visible address, the `PostalAddress` in the NGO structured data, and the Google listing all have to agree, so they derive from one file rather than being written down three times. Two things it encodes that aren't obvious:
  - **The postal code is deliberately NOT in Sanity's `siteSettings.address`.** That string has a trailing `, Cape Town` stripped off before it becomes `streetAddress` (the locality is asserted separately, and stating the city twice in one address is wrong). Appending the code to the Sanity value would stop the string ending in `Cape Town`, the regex would silently stop matching, and `streetAddress` would quietly start including both the city *and* the code. `displayAddress()` appends it at render time instead, so Kerry can rewrite the street line freely without knowing any of that.
  - **`contact.astro` used to hardcode its own copy of the address**, duplicating the Sanity value; it now reads `getSiteSettings()` like the footer does. That page is the likeliest one for Google to read the address off, so it was the worst place on the site for a duplicate free to drift.
- **Opening hours now have one source: `src/lib/opening-hours.ts`.** The contact page's visible `<dl>` and the `openingHoursSpecification` in `Layout.astro`'s NGO block both derive from the same 24-hour values (display strings are *formatted*, not written twice) — structured data contradicting visible copy is worse than omitting it. The hours match the live old site exactly. **⚠ Visits are by appointment, not drop-in**, and schema.org can't express that on `OpeningHoursSpecification`; the qualifier lives in visible contact-page copy and as GBP's "by appointment only" attribute. Don't publish these hours anywhere that can't carry that caveat.
- **Still outstanding:** no intent-matched pages exist for the highest-volume asks (donate goods, volunteer, corporate/CSI partnership — the last is buried inside `get-involved` and is likely the least contested, highest-value intent). Blocked on Kerry's answer about which audience comes first.

## RFC page: how replies are recorded (built 2026-08-15, first batch from Shan)
Shan (social media manager) answered 12 of the 21 questions by email while Kerry was on leave. The page previously had a binary `answered?: boolean`, which couldn't express the state most of those replies were actually in — **a reply is not the same thing as a decision**, and several of them are Kerry's call, not Shan's.

- **Each question now carries an optional `answer: { from, on, text, outcome?, followUp? }`**, rendered as a neutral panel under the question. `from` is load-bearing rather than decorative, since two people reply at different times.
- **`answered` was deleted; settled is derived** — `isSettled(q) = q.answer && !q.answer.followUp`. A hand-set boolean sitting next to a `followUp` is one edit away from marking a question closed while the page visibly still asks for something, and that contradiction would show up on the client's own page rather than in a log. **Add a `followUp` to reopen; remove it to close.** There is no other switch.
- **Three status chips, not two**: grey "Awaiting your answer", amber "<name> replied", green "Answered". Amber is already this page's "in motion, not finished" colour (the Test-mode chip, the question numbers); green must stay reserved for done.
- **The copy-to-clipboard email carries replies into it**, quoted, with `What we did` / `Still open` beneath. Settled questions still drop out entirely but **keep their page numbers** — the existing numbering-stability rule is unchanged and is why answered questions are greyed rather than removed. Without the quoting, the email would re-ask Kerry something Shan already answered as if nobody had read it.
- **Only 2 of the 12 were closed outright** (the postal code, and "ask EF Ogle for the photos" — Shan's answer was that she *is* EF Ogle). Everything else kept a `followUp`, deliberately: Shmiley's "own look" has a real cost attached and is Kerry's; the "homeless" wording is about how the org describes the people it serves; and the consent-form answer needs the form actually read before anyone is named on a permanent, name-searchable public page. **Don't close these by treating a reply as sign-off** — that was the explicit instruction from the user, and it's the reason the middle state exists at all.

## `llms.txt` is generated, not a static file (changed 2026-08-15)
Lives at **`src/pages/llms.txt.ts`**, an Astro endpoint, not `public/llms.txt`. It began as a static file and had silently gone stale in exactly the way static files do: it listed **7 pages when the site had 21**, and named **none of the 11 products** — so the file whose entire job is to tell an answer engine what's on the site was actively contradicting it, and had been since the per-product pages landed. Everything is now derived from the same Sanity queries the pages render from.

- **It says "homelessness" plainly, and that's the point.** The old version described "helping people move from crisis to dignity" and never used the word once — the identical gap found in the page titles and meta descriptions (see "Core-site discoverability"). A model asked "which charities help homeless people in Cape Town" has to be able to match on the word people actually use. ## RFC page: length, and why it isn't split into pages (2026-08-15)

Measured rather than eyeballed — `visible on load` is the number that matters, and it was **4,911 words (~25 min)**, of which **1,670 were the answer blocks added that same morning**. Those had ignored the page's own convention (context collapses, everything else doesn't) and put up to three permanent paragraphs on each of twelve questions. Now **2,459 visible (~12 min)**, 69% of the page collapsed.

**Splitting into separate pages was considered and rejected**, and the reasons are structural rather than aesthetic:
- The **copy-questions button** gathers every outstanding question into one email. Split pages either break that or need it duplicated per page.
- The **`beforeprint` handler** expands every `<details>` so Kerry can print or PDF the whole thing. Splitting breaks "print it all".

- It's a document sent as one link and read once or twice; navigation overhead is paid on every visit.

**Breadcrumbs were asked for specifically and are the wrong control.** They express a position in a *hierarchy*; these sections are siblings in one flat document, so they'd assert a tree that doesn't exist — and in the header they'd imply this internal page is part of the site's structure, which is what the amber nav link exists to deny. A sticky **table of contents** answers the actual question ("where am I, how much is left").

Three things to keep working:
- **`.fk-toc` counts are read off the same arrays the sections render**, so a number can't drift from its section.
- **Scroll-spy is scroll-position based, not an IntersectionObserver.** The sections are far taller than the viewport, so at any moment either several intersect or — inside the questions section — nothing enters or leaves for thousands of pixels and the observer stops firing. The threshold sits **24px below the two sticky bars**: `scroll-margin-top` deliberately leaves a gap, so without that tolerance an anchor jump lands just short of its own line and highlights the *previous* section. It was off by exactly that before the tolerance went in.
- ⚠ **The `beforeprint` selector must list every collapsible.** Screen reading and printing want opposite things here — the more the page collapses, the more a printout silently loses. It currently covers `.fk-ask-context, .fk-ask-more, .fk-live-disclosure`; add any new `<details>` at the same time. ## The favicon — the real brush ring, thickened (rebuilt 2026-08-15)
The tab icon was the full logo (two lines of brush lettering, "est 2014", the teal brush ring) scaled to 32px, where it rendered as an unreadable grey smudge. Now **the logo's own hand-lettered "S" and "T" inside the logo's own brush ring**, on a transparent background.

- **The brush ring works after all — it just needs dilating.** An intermediate version replaced it with a drawn circle, on the finding that the brush stroke breaks into disconnected specks below 32px. True, but the fix is thickening rather than replacement: a `MaxFilter(25)` over the extracted stroke fills the hairline breaks that disintegrate on downscale while keeping the irregular edge and the gaps, which a drawn circle loses entirely. **Don't substitute a geometric circle** — it costs the whole hand-drawn character for nothing.
- **Everything is lifted from `../souper-troopers-media/Branding/ST-primary-logo-COLOUR.png`, not typeset or drawn**: the ring is the teal mask, the letters are the "S" of SOUPER and the "T" of TROOPERS. Both letters are taken **as connected components, not as bounding-box crops** — a crop of the S also catches a slice of the neighbouring O, which shows up as an inexplicable thin vertical line down the S's right side. `scipy` isn't installed; a BFS flood fill over the numpy array does the labelling.
- Letters are **normalised to a common cap height** (on the logo's arc the top line is set larger, which reads as a mistake once two letters stand alone) and lightly **emboldened with a `MaxFilter`**, since brush strokes lose their thin joins first when downscaled. They sit at **0.50 of the canvas** — the monogram is near-square, so its *corners* reach the ring before its edges do; larger values visibly collided with the ring at 48px.
- **The background is transparent, which forces a dark-mode variant.** Ink letters on no background are a near-invisible black void against a dark browser tab strip — verified by compositing over `#202124`, not assumed. So `favicon-32-dark.png` / `favicon-512-dark.png` are identical but with white letters, selected via `media="(prefers-color-scheme: dark)"` on the `<link rel="icon">` tags in `Layout.astro`.
  - **`favicon.ico` is the exception and keeps an opaque white disc.** Browsers fetch `/favicon.ico` by convention even when link tags point elsewhere, so the one icon that can land on an unknown tab colour has to carry its own background. Don't "make it consistent" with the transparent PNGs.
  - **`apple-touch-icon.png` is full-bleed opaque white with an inset ring.** iOS applies its own squircle mask, so a circle in a transparent square floats undersized and transparency can render black.
- **The honest trade**: clearly more Souper Troopers at 32px and above, softer at 16px than a geometric mark would be. Acceptable because 16px only applies on standard-DPI displays — retina/HiDPI, which is most modern laptops and every phone, uses the 32px asset.
- Kerry hasn't chosen this, only had it applied — same pattern as the share card. It's on the RFC page under **"Choices worth knowing about"** rather than as a numbered question, deliberately: it's low-stakes and reversible, and a 22nd question would have renumbered the group Shan already answered against.

## Masonry layouts — which of the two to use (added 2026-08-11)
There are deliberately two mechanisms, and the choice is about **reading order**, not looks:
- **`src/components/Masonry.astro`** — CSS Grid plus ~30 lines of vanilla JS that measures each item and sets `grid-row-end: span N`. Items flow **left-to-right in DOM order**. Use this by default, and always where sequence carries meaning. No dependency; degrades to a plain equal-height responsive grid if the script doesn't run. Accepts `min` (column width) and `gap` props.
- **`.story-masonry` (`our-work.astro`) / `.pay-masonry` (`donate.astro`)** — plain CSS multi-column, global CSS in `Layout.astro`. Fills column 1 top-to-bottom *before* starting column 2, so item 2 sits below item 1, not beside it. Fine for these two, which are unordered sets; wrong for anything sequential.

**Migrating those two to `Masonry.astro` was considered and declined (2026-08-11).** Zero-JS CSS columns have no layout-shift risk at all, and both live on public pages where that matters — CLS is a ranking signal, which cuts directly against the discoverability work above. Neither page needs order today, and swapping is a one-line change on the day one does. **The likely trigger is the donate page**: if Kerry answers the open "which donation channel is most used?" question and the "Ways to give" cards get reordered by actual usage, column-wise fill would undermine it — with 6 cards in 3 columns the top row reads 1, 3, 5, not 1, 2, 3. Switch `pay-masonry` to `Masonry.astro` at that point, not before.

**Gotcha — why `Masonry.astro`'s script is `is:inline` and sits immediately after the grid element.** An ordinary Astro `<script>` is bundled as a deferred module, so it runs after the document parses and usually *after first paint*: visitors see the plain grid render and then visibly snap into the packed layout. Placed inline directly after the grid, it runs synchronously the moment that element has been parsed, so the packed layout is what gets painted first. Don't "tidy" it into a normal `<script>` — that silently reintroduces the shift. Consequences of being inline, both deliberate: it's plain JS (inline scripts are passed through untouched, no TypeScript, no bundling), and it's duplicated once per instance on a page, hence the `window.__stMasonry` shared-function guard. It finds its own grid via `document.currentScript.previousElementSibling`, so instances don't need ids.

**Residual shift that is NOT fixable in the component**: `.fonts-pending` sets `color: transparent` until Quicksand loads, and the fallback font's metrics differ, so card heights change when the real font lands. The `ResizeObserver` re-packs at that point. This reflow is site-wide, not masonry-specific — masonry just makes it more visible, because cards move vertically instead of only re-wrapping.

Native `grid-template-rows: masonry` would replace both approaches, but as of 2026 it's still flagged in Firefox and unshipped elsewhere.

**`.grid-fill` — use it on any grid whose item count is data-driven (added 2026-08-11).** `.grid-2/3/4` use `repeat(auto-fit, ...)`, and `auto-fit` *collapses* empty tracks, so a grid holding fewer items than columns stretches them across the whole row. That's fine for a deliberately short row of text cards and wrong wherever the count comes from content — it was found on `/shop/gift-tags/<item>/`, where "More from" had one sibling left and rendered its thumbnail at **1012px against the actual product photo's 510px**. `.grid-fill` (used *alongside* `.grid-N`, not instead of it) swaps in `auto-fill`, which keeps the empty tracks so items stay one column wide however few there are. The tell is a card containing a square image, since the image scales with the card.

## Colour is an affordance — teal on text or button shapes means interactive (added 2026-08-11)
**The rule: a teal on *text*, or on a *button-shaped element* (pill/circle with a saturated fill and white bold centred label), means you can act on it. Static text, figures, labels and badges use `--st-ink` or a muted `rgba(36, 35, 43, …)`, never a teal.**

**Teal as ambient surface is explicitly fine** — gradients, hairline borders, decorative rules, low-opacity tints, section backgrounds. Affordance is read from a bundle of signals (colour **+ shape + position + typography**), not hue alone, and nobody tries to click a section background. Two reasons this is deliberate rather than a loophole: a brand colour banned from all decoration stops being a brand colour (this teal is from the official brand document), and if teal marked *everything* interactive equally there'd be no hierarchy left — a primary CTA can't outrank forty teal links sharing its colour. The intended stack is: saturated fill + pill = primary action; `--st-teal-dark` + underline = link; tint/border/gradient = brand surface; ink = static content.

Established by an audit of every page and component on 2026-08-11, after the palette had no reserved action colour and the two had drifted together. The worst case was the shop cards, where the coding was **exactly inverted**: `.item-card-price` was bold teal-dark while the product-name link directly above it was `color: inherit` + `text-decoration: none` — so the static price looked like the link, and the actual link looked like static text and was invisible to anyone not hovering (i.e. every touch user). Prices, stat figures, press eyebrows, B-BBEE values, payment icons and `.badge`/`.badge-on-dark` all moved to ink.

**`.impact-stat strong` is white, not a teal — don't put it back.** It was moved to `--st-teal-light` in the first pass on brand-family grounds, which was wrong: it's still teal on static *text*, and it contradicted `.stat strong` (identical content type) going all the way to ink. `.path-fact` had already settled this exact question — see its comment: a static figure at that size doesn't need a colour to stand out. White also takes it 9.42:1 → 15.55:1.

**Corollary — don't put `text-decoration: none` on a body link.** There is deliberately no global underline reset, so prose links inherit the browser's underline and that is the non-colour cue colour-blind visitors rely on. Several links had opted out and styled themselves on `:hover` only, which is not an affordance on touch. `.item-card h3 a`, `.back-to-category a`, `.cart-empty-link`, `.back-link` and `.breadcrumbs a` were all fixed this way. Hover may change *colour*; it must not be what reveals that a thing is a link at all.

**Deliberately left teal — don't "fix" these:**
- **Ambient surfaces** (the large category, per the rule above): the `.hero`/`.stories-band` gradients, `.quote`'s left border, the CAST connector rule, `.badge`'s 12% tint, the contact toast background, the homepage BrushRing. Also anything inside an `<a>` wrapper, which is correctly interactive: `.category-tile-cta`, `.action-cta`, `.path-*`, `.cart-count`.
- `.glow-word` (`Layout.astro`) — animated emphasis word in headlines. The one intentional teal-on-static-text exception: it's a documented feature, and nothing around it is clickable.
- `.cast-letter` / `.step-number` — filled teal circles marking sequence steps. **The weakest remaining case, and knowingly accepted**: saturated fill + circle + white bold text is both button-coloured and button-shaped. What saves it is context — C-A-S-T and 1-2-3 in an obvious sequence read as ordinal markers, not controls. Changing them is a redesign rather than a recolour, so it needs a design decision, not a token swap.

**Two contrast problems the audit found that are NOT fixed, because fixing them means touching brand tokens or a section's design:**
1. **`a { color: var(--st-teal-dark) }` is 4.29:1 on `--st-bg`** (`#faf9f6`) — every ordinary prose link on the site is marginally under the 4.5:1 AA threshold. It clears AA on white cards (4.52:1) but not on the page background.
2. **`.stories-band`'s white body copy is 2.76:1** at the teal end of its gradient — the whole band is under AA, not just links. A link on it was far worse (1.09–1.64:1, effectively invisible) until `.stories-band a { color: inherit }` was added; that brought the link to parity with its neighbours but did not fix the band.

Also noted and left alone as out of scope: `.btn-secondary` is white-on-green at **2.42:1** and `.btn-primary` white-on-teal at **2.76:1**. Both fail AA for their 16px bold labels. Fixing either means changing a brand colour or the button system.

**Confirmed by Lighthouse 2026-08-13 — the above hand-audit was right, and there is a third family it missed.** Run on `/`, `/donate`, `/contact` (a11y 91→96 after the touch-target fix below). Every `color-contrast` failure across the three pages reduces to just three colour pairs:
1. **White on `--st-teal` (`#1babbe`) = 2.75:1** — `.btn-primary`, 7+ instances/page. The single biggest contributor, and still a brand/button-system decision, not a recolour.
2. **`--st-teal-dark` (`#148294`) on `--st-bg` = 4.28:1** — ordinary prose links, as documented above.
3. ~~**Muted ink greys below `0.65` alpha**~~ — **fixed 2026-08-13**, and it was never a brand question: these are just opacity levels on `--st-ink`. Was `rgba(36, 35, 43, 0.42–0.64)` on `dt`, `.redirect-note` and small print, landing at 3.53–4.20:1.
   - **The threshold is alpha `0.65`, and one value covers every background this site uses** — computed, not guessed: `0.65` gives 4.75:1 on `--st-bg` `#faf9f6`, 4.91:1 on white cards, 4.75:1 on `#f6f6f7` tinted cards and 4.51:1 on the `rgba(36,35,43,0.08)` pill tint (`.badge`, `.fk-ask-number`), where `0.60` gives 3.91–4.20. So **`0.65`+ passes and `<0.65` fails, whatever it sits on** — use `0.65` as the floor for any new muted text rather than re-deriving it.
   - 18 declarations were raised. The **one deliberate exception is `.cart-empty-icon` at `0.18`** — a decorative glyph, not text, with `.cart-empty-text` saying the same thing in words beside it; there's a comment on it so it doesn't get "fixed".
   - **Two of them were invisible to the obvious grep.** `grep -rn "color: rgba(36, 35, 43, 0\.[0-9]*)"` misses (a) single-digit alphas like `0.6` if the pattern demands two digits, and (b) **unspaced inline styles** — one failure was `style="…color: rgba(36,35,43,0.6);"` in `donate.astro`, in the markup rather than a `<style>` block. Search `rgba(36,\s*35,\s*43` and check `style="` attributes too, or the audit will keep reporting a node the grep says doesn't exist.

**Touch targets — `target-size` now passes; keep it that way when adding icon buttons (fixed 2026-08-13).** `CopyButton.svelte` was a bare 14×14 icon with `padding: 0`, against WCAG 2.2's 24×24 minimum. **The fix has to grow the button's own border box** — axe measures `getBoundingClientRect()` on the element, so the usual `::after` hit-area overlay improves the real tap target but still fails the audit, because a pseudo-element does not enlarge its parent's rect. Now `min-width/min-height: 24px` with the icon left at 14px. Two things worth not undoing: **height was free** (the inline line box these sit in already measured 24px, so only width changed, by ~10px), and there is **deliberately no negative margin** clawing that width back — it would overlap the adjacent mailto link's rect, trading a size failure for mis-taps on the wrong control.

## Link prefetching — `prefetch: true` on its own prefetches nothing (fixed 2026-08-13)
Reported as "other pages still load lazily when I tap through from home on my phone", against a config that already said `prefetch: true` and a commit titled "Enable hover prefetch". **It had never prefetched a single link, on any device** — the flag only ships the prefetch *runtime*; it opts no links in. In Astro's `elMatchesStrategy` (`node_modules/astro/dist/prefetch/index.js`) a link matches only if it carries `data-astro-prefetch` **or** `prefetchAll` is on, and `prefetchAll` defaults to `false`. There were no such attributes anywhere in `src/`, so every link failed every strategy. Confirmed in the built bundle: the injected constants were `undefined`, falling through to `prefetchAll = false` / `defaultStrategy = "hover"`.

**The tell that this is the failure mode, not a slow network: nothing changes on desktop either.** Verify at the bundle, never at the config line — `grep -o "prefetchAll??[^,]*" dist/_astro/page.*.js` shows only the unchanged *fallback* expression and looks identical either way; the real values are the bare initialisers near the top of that module (``r=!0,i=`viewport` `` when set, `undefined` when not).

Now `prefetch: { prefetchAll: true, defaultStrategy: 'viewport' }`. Two things worth not undoing:
- **`viewport`, not the `hover` default.** `hover` is pointer-only; on a touch device it can at best fire on the tap that is already navigating, which is why this was noticed on a phone.
- **The six nav links in `Layout.astro` additionally carry `data-astro-prefetch="load"`, and need it.** Under 760px the nav is `translateY(-100%)` behind the hamburger, so an IntersectionObserver never sees it — measured at 390px it sits at `top: -379px`, `visibility: hidden`. `viewport` alone would therefore have skipped the primary nav on exactly the device the complaint came from. `load` ignores position and fetches at idle. Affordable because it is the *fixed* nav: ~10KB gzipped × 5–6 docs, less than one hero photo, and the same six on every page so they are cache hits after the first.

Astro skips prefetch entirely when the browser reports Save-Data or a 2g connection, so this stays polite on poor connections; Netlify bandwidth (20 credits/GB) stays noise at this traffic. **This is still a static MPA with no `ClientRouter`** — prefetch removes the blocking HTML round-trip, it does not make navigation SPA-instant. View transitions are the next lever and are a per-page behavioural change, so they need the user's sign-off, not a quiet add.

## Development
**`npm run build` typechecks first (added 2026-08-11):** the script is `astro check && astro build`, with `@astrojs/check` + `typescript` as devDependencies and a standalone `npm run check`. Before this, `astro build` did no typechecking at all, so the build went green while the editor showed errors. It immediately found a real one: `src/lib/sanity.ts` imported `SanityImageSource` from `@sanity/image-url/lib/types/types`, a v1 path that doesn't exist in v2 (whose `exports` map blocks subpaths entirely) — the type had silently been `any`, leaving every image-URL call unchecked. **`tsconfig.json` excludes `studio` entirely, and must stay that way.** `studio/` is a separate package with its own `package.json` and `tsconfig.json`; Netlify only installs the root dependencies, so on CI the Studio's imports (`sanity`, `@sanity/vision`) resolve to nothing. Excluding only `studio/dist` looked fine locally — `studio/node_modules` exists on a dev machine — and **broke the production deploy with 45 errors**, on 2026-08-11. A green local build cannot catch this by construction; to reproduce CI, `mv studio/node_modules` aside and build. Typecheck the Studio from inside `studio/` if it ever needs it. Verified the gate actually blocks: a deliberate type error aborts before `dist/` is written.

**The exact mirror of that, found 2026-08-12 — the two packages break each other in both directions.** The `Deploy Sanity Studio` workflow failed on its first real run with `Tsconfig not found astro/tsconfigs/strict`. `sanity build` runs Vite, and its rolldown resolver scans up out of `studio/` and reads the **repo-root `tsconfig.json`**, which opens `"extends": "astro/tsconfigs/strict"` — and `astro` lives in the *root* `node_modules`, which that workflow didn't install. Fixed by adding a root `npm ci` to the workflow purely so that one `extends` resolves; nothing there builds the site. **Reproduce with `mv node_modules/astro` aside, then `npx sanity build` from `studio/`** — it cannot fail on a dev machine otherwise, since both installs always exist. Tried and rejected: removing `exclude: ["node_modules"]` from `studio/tsconfig.json` (the resolver finds the root config regardless of include/exclude — tested). The remaining alternative is hiding the root tsconfig for the duration of the build, which works but reads as sabotage in review. **Rule of thumb: any CI job that builds one of the two packages needs the other's dependencies too, for reasons that never show up locally.**

**Test a workflow change without merging it to `main`: `gh workflow run "<name>" --ref dev`.** `workflow_dispatch` runs the workflow definition *from the ref you name*, so this executes `dev`'s version. GitHub's default-branch rule (documented above for the backup workflow) only governs whether a workflow is *dispatchable at all* — once the file exists on `main`, other branches' versions can be run freely. This is what verified the tsconfig fix above: dispatched on `dev`, passed in 1m31s, `Success! Studio deployed to https://souper-troopers.sanity.studio/`. **It touches GitHub Actions only — no Netlify build, no production deploy, no credits** — which matters whenever the Netlify allowance is exhausted, since merging to `main` is otherwise the only way to exercise a workflow. Needs the `Memeplexx` account (see the auth note above). Minor outstanding: `actions/checkout@v4` and `actions/setup-node@v4` still target Node 20 and now warn on every run; bump to v5 when convenient.

**`npm run dev` (repo root) starts all three dev processes together** via `concurrently`, labeled/color-coded in one output stream — Ctrl+C stops all three: the Astro site (:4321), the Sanity Studio (:3333), and a `netlify dev` proxy (:8888) that serves the local `netlify/functions/` (`create-payfast-payment`, `payfast-itn`) on top of the Astro site. Plus a fourth, short-lived `check` process — see the stale-server guard below.

**A running dev server is not necessarily a working one — two scripts now guard this (added 2026-08-13, after it cost a full session).** Symptom: every local image missing site-wide, while Sanity CDN images kept working and every page rendered fine. Cause: an `astro dev` that couldn't resolve `sharp` at startup. Node caches a failed `require` for the life of the process, so `/_image` returned 500 forever without ever retrying — and that process had been up three and a half days. What hid it was port drift: **`astro dev` does not fail when :4321 is taken, it quietly takes :4322**, so a *healthy* second server was running on a port nobody was watching while `netlify dev` (pinned to `--target-port 4321`) kept proxying :8888 to the broken original. Everything reported success.
- **`scripts/free-dev-ports.mjs`** runs as `predev`, so every `npm run dev` starts from known-good processes. It frees :4321/:3333/:8888, but **only from processes whose argv contains this project's path** — anything else and it *stops the whole run* rather than continuing, since silently leaving a foreign process on :4321 just recreates the drift. Consequence worth knowing: a second `npm run dev` in another terminal replaces the first one's servers instead of racing onto shifted ports. Astro's own lock file (`.astro/dev.json`, `astro dev --force`) does not cover this — it tracks only its own server, and the stale one here was untracked, so `--force` would have skipped it and drifted again.
- **`scripts/check-dev-assets.mjs`** runs as the `check` pane (or on demand via `npm run dev:check`) and fetches a real `/_image` asset **through :8888, not :4321** — the proxy hop is itself a place this breaks, so testing Astro directly would pass while the URL you actually browse stayed broken. One line on success; on failure it prints Astro's own error plus the remedy. Both paths were verified by reproducing the real fault (`mv node_modules/sharp` aside), not just by reasoning about them.
- **`sharp` is only an *optional* dependency of `astro`, so it is now a declared one of ours too** (`dependencies`, not dev — the production build needs it; it dedupes against Astro's copy rather than adding a second). Optional installs can be skipped silently — platform mismatch, flaky network, `--no-optional` — and that is exactly what this failure mode looks like; declaring it turns a skipped install into a loud `npm install` failure instead of a runtime mystery days later. Only Astro's `/_image` endpoint needs it, which is why local `src/assets/images/*` break while Sanity CDN URLs keep working: **that split is the diagnostic tell.**

**Browse the site at `http://localhost:8888`, not `:4321`, during local dev.** `:4321` is the raw Astro server — it has no idea `netlify/functions/` exists, so anything that calls `/.netlify/functions/*` (e.g. the Shop checkout) 404s there. `:8888` is `netlify dev`'s proxy: same site, same content, but with working functions layered on top. (Previously these were two separate scripts, `dev` and `dev:functions` — merged 2026-08-09 after this split caused real confusion: browsing the default `npm run dev` port and hitting a function-not-found error on Shop checkout. No real downside to merging — `netlify dev` here reads secrets from the local `.env`, not a linked Netlify account, so it doesn't add any auth requirement.)

**Gotcha (why the `dev` script is built the way it is)**: `netlify dev`'s normal framework auto-detection is not usable in this project — running it plain hits an interactive "Multiple possible dev commands found" prompt (Astro vs. Svelte both resolve to `npm run dev`), which hangs forever in a non-interactive/agent session. Passing `--command "npx astro dev"` directly doesn't work either — Astro's dev server daemonizes itself immediately (prints "Dev server running" and returns control), which `netlify dev` misreads as the framework process crashing, so it shuts itself down right after starting. The fix baked into `package.json`: `netlify dev` is given a no-op long-running placeholder command (`--command "tail -f /dev/null"`) alongside `--target-port 4321` — it just needs to see port 4321 already answering (which `concurrently` starts in parallel) and proxies to it; what its own supervised "command" does doesn't matter as long as it doesn't exit.

Reads `.env` automatically for local secrets (`PAYFAST_MERCHANT_ID` etc.). `URL` is auto-injected by `netlify dev` to match its own local address, so PayFast's `return_url`/`notify_url` correctly point at `localhost:8888` during local testing without any extra config.

When starting it in the background (e.g. so an agent session isn't blocked on it), run the underlying processes directly rather than through the unified `npm run dev` — `astro dev --background` for Astro (managed with `astro dev stop`, `astro dev status`, `astro dev logs`), `sanity dev --port 3333` from `studio/` for the Studio (backgrounded via `nohup ... &`, stopped via `pkill -f "sanity dev"` — no background-mode flag of its own), and `netlify dev --command 'tail -f /dev/null' --target-port 4321 --no-open` for functions (same `pkill -f "netlify dev"` pattern) once Astro is confirmed up.
